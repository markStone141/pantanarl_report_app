# 共通ボタンUI展開計画（工程11）

最終更新日: 2026-08-12

## 目的

共通メニュー／NAVで確定した、青を基調とする落ち着いた色、控えめな境界線、適度な角丸、明確な現在状態の雰囲気へ、各画面の操作ボタンを統一する。機能名や操作順を変えるのではなく、操作の重要度と状態が全アプリで同じ見た目・操作感になることを目標とする。

## 現状

- 共通の `.btn-inline` は多数の画面で使われているが、主要操作と補助操作の差が弱い。
- `dairymetrics`、`talks`、`testimony`、`mosaic`、`monthly_guide` などにアプリ固有ボタンが残り、色、角丸、高さ、境界線、hover、disabledが異なる。
- アイコン、フィルタ、タブ、危険操作が画面ごとに異なる意味の色を使っている。
- 送信中・選択中・無効状態は実装済みの画面が多いが、見た目の規則が共通化されていない。

## 設計原則

1. メニュー／NAVの視覚言語を基準にする。
2. 主要操作は1画面または1操作群につき原則1つに絞る。
3. 通常・補助操作は白または淡い面、細い境界線、濃い文字で表現する。
4. 危険操作は常時強い赤で塗らず、通常時は控えめにし、hover・focus・確認画面で危険性を明確にする。
5. 選択中、送信中、成功、失敗、無効を色だけで表現しない。
6. タブ、フィルタ、スイッチは送信ボタンと同じ見た目にせず、選択操作として区別する。
7. 固有機能の名称、URL、権限、フォーム送信、AJAX、確認処理は変更しない。

## 共通ボタン体系

| 種別 | 用途 | 想定クラス | 見た目の基準 |
|---|---|---|---|
| Primary | 保存、登録、送信、次へなど主要操作 | `.ui-button--primary` | NAVのブランド青、白文字、明確なfocus |
| Secondary | 編集、戻る、詳細、補助的な遷移 | `.ui-button--secondary` | 白または淡色面、細い境界線 |
| Quiet | キャンセル、閉じる、低優先リンク | `.ui-button--quiet` | 面を強調せず、hoverで操作性を示す |
| Danger | 削除、無効化、終了など不可逆操作 | `.ui-button--danger` | 控えめな赤系境界・文字、確認時に強調 |
| Icon | 編集、削除、お気に入り等の小操作 | `.ui-icon-button` | 正方形、共通サイズ、ツールチップ／aria-label必須 |
| Choice | タブ、フィルタ、表示切替、タグ選択 | `.ui-choice-button` | 選択中を背景・境界・文字・ariaで示す |

共通状態として `:hover`、`:focus-visible`、`:active`、`:disabled`、`[aria-pressed="true"]`、`.is-active`、`.is-loading` を定義する。ボタン高、左右余白、アイコン間隔、角丸、フォーカスリングは共通トークンを使う。

## 対象

- 11アプリのテンプレートにある `button`、ボタン型 `a`、`input[type=submit]`。
- `app.css`、`ui_foundation.css`、各アプリ固有CSSにあるボタン規則。
- PC／モバイル、通常／hover／focus／active／disabled／loading、空状態内の操作。
- 管理者だけに見える編集・削除・設定操作と、一般利用者向け主要操作。

## 対象外

- 共通NAV自体の再設計。
- URL、View、Form、Model、認証、権限、集計ロジックの変更。
- 文言や操作順の大規模な変更。
- 記事カードや長文レイアウトの全面再設計。

## 実行工程

### 11-1: ボタン台帳と基準UIの確定

- 全テンプレート／CSSからボタンを抽出し、上記6種へ分類する。
- `dashboard` と `performance` の代表画面で共通クラスを試験適用する。
- NAVと並べたときの色、角丸、高さ、余白、focusをPC／モバイルで確認する。
- 同じ操作に複数の見た目が割り当てられていないか確認する。

状態: 2026-08-12 完了。`dashboard` と `performance` の代表画面へ適用し、PUSH前確認用の `docs/button-ui-preview.html` を追加した。

完了条件:

- 共通クラスと状態が `ui_foundation.css` と `UI_FOUNDATION.md` に定義される。
- 主要／通常／補助／危険／アイコン／選択操作の区別が代表画面で確認できる。
- 既存の送信処理、権限、テストが維持される。

### 11-2: 管理・設定・日常入力系

対象: `dashboard`、`performance`、`targets`、`mail`、`reports`、`dairymetrics`

- 保存・登録・送信をPrimaryへ統一する。
- 戻る・編集・詳細をSecondaryまたはQuietへ整理する。
- フィルタ、表示切替、段階操作をChoiceへ移す。
- 削除、無効化、活動終了をDangerとして区別する。
- 既存の送信中表示と二重送信防止を維持する。

状態: 2026-08-12 完了。`dashboard`、`performance`、`targets`、`mail`、`reports`、`dairymetrics` の主要操作、補助操作、危険操作、表示切替へ共通体系を適用した。ページ番号リンク、NAVトグル、グラフ内の日付操作、フローティング検索ボタンなど固有配置に依存する操作は、工程11-4で競合を監査する。

### 11-3: 閲覧・検索・独立アプリ系

対象: `talks`、`testimony`、`monthly_guide`、`mosaic`、`accounts`

- お気に入り、反応、タグ、検索条件をChoice／Iconへ整理する。
- 投稿、コメント、接客ログ、ログインの主要操作をPrimaryへ統一する。
- コピーなど固有操作は機能を維持しつつ共通サイズ・状態へ合わせる。
- 独立アプリのブランド名や長文表示は維持する。

### 11-4: 横断監査と公開前確認

- 旧クラスが残る場合は固有要件か移行漏れかを記録する。
- 全URL、権限、フォーム、AJAX、戻る操作、キーボード操作を回帰確認する。
- PC／モバイルでボタンの折返し、全幅化、タップ領域、固定要素との重なりを確認する。
- 未使用CSSを削除し、詳細度競合や `!important` の増加がないことを確認する。

## 工程単位の進め方

- 1コミットは原則1アプリまたは密接な関連アプリ群、変更10ファイル以内にする。
- 各単位を `監査 -> 分類 -> 実装 -> frontend_interaction確認 -> ui_designer確認 -> 対象テスト -> 全体回帰 -> コミット` の順で進める。
- 10ファイルまたは500行を超える場合は無理に同一単位へ含めず、次の単位へ分割する。
- PUSHと公開は明示指示があるまで行わない。

## 検証項目

- Django対象テストと全体テスト。
- `python manage.py check`、migration差分、BOM、EOF、`git diff --check`。
- JavaScript構文と、利用可能になった場合はnpm lint。
- Enter送信、連続クリック、送信中、通信失敗、disabled解除。
- `:focus-visible`、Enter／Space、`aria-pressed`、`aria-label`。
- 一般利用者に管理・危険操作が表示されないこと。
- 320px相当の狭い画面でもラベルが読め、隣のボタンを誤操作しにくいこと。

- 操作の重要度と危険性が見た目で区別できる。
- 既存機能、権限、送信状態、URL、AJAXに回帰がない。
