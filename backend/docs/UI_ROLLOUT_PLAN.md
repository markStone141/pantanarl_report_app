# 全アプリUI展開計画

最終更新日: 2026-08-12

## 目的

`performance` 管理者画面で整えた情報設計を基準に、共通ルールの上へ各アプリ固有の操作を載せる。変更は原則として、1アプリまたは関連アプリ群ごとに `監査 -> UI案 -> 実装 -> PC/モバイル確認 -> テスト -> コミット` の単位で進める。

## 全工程

### 工程1: Performance基準UIの確定（完了）

対象:

- `performance` 管理者ダッシュボード
- 本日の活動状況、本日の記録、目標達成率、全体実績推移
- 有効メンバー一覧

追加要件（有効メンバー一覧）:

- 各メンバーの最近の実績を一覧で確認できる。
- 直近3回の「活動終了済み稼働」を時系列で表示する。
- 3稼働連続0件のメンバーを一目で判別できる。
- 3稼働連続1件以上のメンバーを一目で判別できる。
- 未報告、活動中、活動終了済み0件を同じ0件表示にしない。
- 状態別件数（すべて、要確認、連続実績あり）を表示し、絞り込める。
- PCでは一覧性を保ち、モバイルでは直近3稼働を横スクロールなしで表示する。
- 行全体の強い塗り分けを避け、状態ラベル、左アクセント、各稼働枠で状態を示す。
- 月累計と路程累計は補助情報とし、直近3稼働より視覚的に強くしない。

現状監査:

- 連続0件／連続実績ありの判定は、直近の活動終了済み3件を使って実装済み。
- 現在の表示用データは直近1件分のみで、判定根拠となる3稼働の日時・件数が画面に出ていない。
- 現在は名前、月累計、路程累計、直近実績が同じ強さの4列で並ぶ。
- 状態該当行は背景全面を赤／青にしており、人数が増えると視認性が落ちる。
- 未報告と活動終了済み0件を表示上で明確に区別するデータ構造が不足している。

完了条件:

- 上記3目的を、説明を読まなくても一覧の第一視線で判別できる。
- 状態判定と表示根拠が一致するテストがある。
- 既存のUN／WV件数表示、補正込み最終実績、個人詳細リンクを維持する。
- PC／モバイル、管理者権限、空状態を確認する。
- 対象テスト、全体テスト、lint、Django check、migration、BOM、差分確認が成功する。

## 工程管理ルール

- 進行中の主工程は1つにする。
- 各工程の開始時に対象、対象外、完了条件、依存関係を `PROJECT_STATE.md` へ記録する。
- 各工程の終了時にテスト、残リスク、コミット、PUSH、公開状態、次工程を更新する。
- PUSHと公開環境確認が未完了でも、ローカルで独立して検証できるUI設計・実装は進める。ただし公開済みとは扱わない。
